🚨 AddrLLM: Address Rewriting via LLM on Nationwide Logistics Data

Yang et al. (2024) | arXiv:2411.13584 | JD Logistics & Rutgers

⚠️ CRITICAL THREAT

Their Methodology

  • Stage 1: SFT with multi-instruction training (60M total)
  • Address Parsing: 20M pairs
  • Address Entity Prediction: 20M pairs
  • Address Rewriting: 20M pairs
  • Stage 2: Vector RAG retrieval (200M geocoding data)
  • Stage 3: Bias-free alignment (4M package delivery data)
  • Output: Rewritten address string (free-text)

Why They Chose This

Problem Context: Nationwide deployment (JD Logistics, 100M+ addresses, 25k rerouting events/day)
  • Scale: 100M+ addresses → vector retrieval more scalable than exact match
  • Diversity: Nationwide China → regional diversity → RAG retrieve similar patterns
  • Flexibility: New addresses without retraining LLM (just re-embed)
  • Unknown patterns: LLM can generate plausible rewrites for unseen formats

Side-by-Side Comparison

Dimension Your Thesis AddrLLM
Training Data Size 230k (synthetic) 60M (real JD LBS system)
Scope Jakarta only (single region) Nationwide China
Retrieval Type Deterministic indexed lookup (AdminVerifier) Probabilistic vector RAG (cosine similarity)
Output Format 12-field JSON with 4-state confidence Free-text rewritten address
Incomplete Data Handling Explicit (Unverifiable state) Implicit (LLM might hallucinate)
Hallucination Risk Minimal (post-hoc deterministic) Moderate (LLM generation + RAG ambiguity)

⚠️ Why AddrLLM Is a Threat

  • Same Problem Framing: "SFT LLM + retrieval module" for address normalization in logistics
  • Similar Pipeline: Two-stage (extraction → retrieval/verification)
  • Scale & Results: 43% improvement on real production data → impressive practical impact
  • Examiner Risk: Dosen might ask: "Isn't this just a smaller, less sophisticated version of AddrLLM?"

🛡️ How to Defend Against This Threat

Key Argument: Different architectural choices for different constraints.

  • Deterministic vs Probabilistic: AddrLLM uses cosine similarity retrieval (can retrieve wrong context if ambiguous). Your AdminVerifier is exact match—if field exists in DB, it WILL be found (no retrieval failure risk).
  • Data Rumpang Modeling: AddrLLM doesn't model incomplete reference data (assumes national DB is complete). Your thesis explicitly designs around Jakarta's 30% null kelurahan, 34% null kodepos. This is not limitation but core design constraint.
  • Output Transparency: AddrLLM outputs rewritten string (how certain is it?). Your 4-state confidence schema is epistemic signal—"Verified" vs "Unverifiable" directly communicates data reliability.
  • Domain-Specific: AddrLLM nationwide China (no RT/RW). Jakarta has micro-administrative RT/RW layer—your system addresses Indonesian-specific challenges.
Bottom Line: AddrLLM optimized for nationwide scale with unknown patterns. Your thesis optimized for single-region deep understanding with data-rumpang awareness. Both are valid but address different constraints.

🚨 AddrKG-LLM: Patient Address Parsing via KG-aware Contrastive Learning

Li et al. (2024/2026) | Scientific Reports | Medical Records Domain

⚠️ CRITICAL THREAT

Their Methodology

  • Stage 1: Knowledge Graph (KG) with contrastive learning
  • Multi-view graph aggregation over admin hierarchy
  • Retrieval: Top-K candidates from KG via cosine similarity
  • Stage 2: Candidate-restricted LLM decoding
  • LLM output constrained to Top-K candidates (bounded search space)
  • Output: Hierarchical JSON tuples with per-field accuracy
  • Privacy: On-premise deployment (no external API calls)

Why They Chose This

Problem Context: Medical records (patient privacy-critical, on-prem required, schema must be strictly enforced)
  • Privacy: Medical data sensitive → on-prem deployment required
  • Hierarchy Awareness: KG topology encodes admin relations → better bounded search
  • Schema Compliance: Candidate restriction prevents invalid outputs
  • Hierarchy Leverage: Contrastive learning aligns embeddings to admin relations

⚠️ Why AddrKG-LLM Is a Threat

  • Most Similar Pipeline: Both are 2-stage, both output hierarchical JSON, both do external knowledge grounding
  • Examiner Risk: "Isn't your AdminVerifier just a non-learned version of their KG + Top-K retrieval?"
  • Complexity Comparison: They use advanced graph ML (contrastive learning, GraphSAGE). You use simple indexed lookup. Question: Is simplicity enough to claim novelty?

🛡️ How to Defend Against This Threat

Key Argument: Deterministic beats probabilistic for incomplete data.

  • Retrieval Failure Risk: AddrKG-LLM Stage 1 returns Top-K set. If gold entry isn't in Top-K (due to embedding miss or KG gap), Stage 2 CANNOT recover. Your AdminVerifier: exact match = guaranteed find or explicit Unverifiable.
  • Data Rumpang Is Core: AddrKG-LLM assumes KG coverage is complete (medical records context). Your thesis explicitly measures Jakarta DB gaps (30% kelurahan null) and designs system architecture around this constraint. This is orthogonal innovation.
  • Confidence Schema Is Unique: AddrKG-LLM reports accuracy metrics (Amicro, Amacro, Recall@K). Your 4-state confidence schema is independent contribution—it reports epistemic state per field to user, not just aggregate metrics.
  • Modularity Advantage: AdminVerifier is post-hoc, non-parametric. Can update DB instantly without retraining. Their KG + contrastive learning requires retraining when KG changes.
  • Modular Advantage Detail: "Their approach is tightly coupled (KG trained into embeddings). My AdminVerifier is loosely coupled (post-hoc verification). For thesis context with evolving Jakarta admin data, modularity is advantage."
Bottom Line: AddrKG-LLM uses sophisticated learned retrieval (good for large, diverse KGs). Your thesis uses simple deterministic lookup + null-honesty (better for single-region incomplete data where "don't know" is legitimate answer).

  • Examiner Risk: "Why build local AdminVerifier when you can just call external geocoding APIs like GeoAgent?"

🛡️ How to Defend Against This Threat

Key Arguments: Different constraints require different solutions.

  • Latency & Privacy: GeoAgent requires API calls each inference (high latency, privacy risk—addresses sent externally). Your AdminVerifier is local indexed lookup (milliseconds, zero privacy leak).

  • Data Rumpang: GeoAgent assumes external APIs have complete coverage. Jakarta data has known gaps (30% kelurahan null). Your system honest about this; GeoAgent would silent-fail or hallucinate.
  • No Confidence Schema: GeoAgent binary output (succeed/fail). Your 4-state confidence reports epistemic state—independent contribution.
Bottom Line: GeoAgent optimized for flexibility + external scale. Your thesis optimized for privacy + transparency + offline-capability. Different design philosophies.

🟠 SLOT: Structuring the Output of Large Language Models

Wang et al. (2025) | arXiv:2505.04016 | Amazon Web Services

⚠️ HIGH THREAT

Their Methodology

  • Post-Processing Approach: Model-agnostic schema correction
  • Fine-tuned Mistral-7B (dedicated post-processor)
  • Constrained decoding (enforces valid JSON)
  • Achieves: 99.5% schema accuracy
  • Works with any upstream LLM (no retraining needed)
  • Result: Schema-compliant JSON with ~94% content preservation

Why They Chose This

Problem Context: LLMs produce semantically valid but structurally invalid JSON (nested brackets, wrong keys, etc.)
  • Generality: Works with any LLM (Claude, GPT, etc.)
  • Simplicity: Single post-processor, no complex pipeline
  • 99.5% Accuracy: Strong structural guarantees
  • Modularity: Can swap upstream LLM without changing post-processor
Dimension Your Thesis SLOT
Post-Processor Type Deterministic domain-specific (AdminVerifier) Learned generic schema-corrector (Mistral-7B)
Responsibility Semantic verification (content correctness) Structural compliance only (format correctness)
Example SLM says "kecamatan: Gambir" → AdminVerifier checks if Gambir valid for Kelurahan 'Ancol' (semantic check) LLM outputs malformed JSON → SLOT fixes brackets, quotes (structural check)
Confidence Schema 4-state (Verified/Inferred/Unverifiable/Free-form) None (just schema compliance)

⚠️ Why SLOT Could Be a Threat

  • Post-Hoc Correction Parallel: Both use post-processing to fix LLM output
  • Examiner Risk: "Why build AdminVerifier when SLOT already does post-hoc fixing?"
  • Simpler Approach: SLOT's constrained decoding is elegant; AdminVerifier is domain-specific lookup

🛡️ How to Defend Against This Threat

Key Argument: Structural compliance ≠ Semantic correctness.

  • SLOT = Structural (what SLOT does): Ensures output is valid JSON (correct brackets, valid keys). Doesn't check if content is accurate.
  • AdminVerifier = Semantic (what you do): Ensures output is factually correct (field values exist in authoritative DB, hierarchy is valid). Structural correctness is prerequisite but not sufficient.
  • Concrete Example:
    • SLOT: {"kelurahan": "Gambir", "kecamatan": "Penjaringan"} → valid JSON ✓
    • AdminVerifier: But is Gambir actually in Penjaringan per Jakarta DB? NO → flag as error
  • Complementary, Not Competing: SLOT handles Layer 0 (schema), AdminVerifier handles Layer 1 (semantics). Could even be used together: SLOT → AdminVerifier pipeline.
  • 4-State Confidence: SLOT doesn't output epistemic state. Your confidence schema is independent contribution.
Bottom Line: SLOT fixes malformed JSON. AdminVerifier grounds JSON in reality (verifies field values against authoritative DB). Different problems, different solutions.

📌 Summary: Novelty Defense & Consolidation

Your Core Novelty Claims (What You Own)

  • [N1] Two-Error-Mode Framework: Decomposes failures into syntactic extraction errors (noisy input) vs semantic verification errors (data rumpang). No competitor explicitly decomposes this.
  • [N2] Deterministic Admin Grounding: Post-hoc indexed exact-match lookup (not RAG, not retrieval). Eliminates retrieval failure + hallucination risk simultaneously.
  • [N3] 4-State Confidence Schema: {Verified, Inferred, Unverifiable, Free-form} as first-class output communicating epistemic state. No competitor outputs this.
  • [N4] Null-Honesty Principle: System explicitly reports missing data (Unverifiable) instead of hallucinating. Operationalized in both corpus (frozen template) and architecture (AdminVerifier).
  • [N5] Data Rumpang as Design Constraint: Explicitly models Jakarta's 30% kelurahan null, 34% kodepos null. Unique to this region, foundational to architecture.
  • [N6] Hybrid Synthetic Corpus: Rule-based injection of realistic admin gaps + external LLM (only for syntactic variation). 230k samples engineered to two-error-mode taxonomy.
  • [N7] Proof of Sufficiency: 8B SLM + deterministic grounding achieves competitive performance at massive cost/privacy savings vs large LLMs.
  • [N8] Indonesian-Specific: Jakarta RT/RW micro-administrative layer + SNI 9037:2021 + Pergub-derived data. Unique to Indonesian context.
